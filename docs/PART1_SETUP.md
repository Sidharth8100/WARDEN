# Part 1: human credential setup and live proof

Agents must not execute the credential generator or read the files it creates.
No deployment credential has been generated by the AI. Existing credential
files are never opened, overwritten, or merged automatically.

## Required human action

Run from the repository root in your own terminal:

```bash
uv run python scripts/provision_part1.py
```

Review the script, then type `CREATE` at its interactive prompt. It uses
`secrets.token_hex(32)` for 256-bit Redis passwords and storage secret keys;
`secrets.token_hex(16)` for storage access IDs. Equivalent individual random-value
command: `openssl rand -hex 32`. The script computes Redis password hashes with
SHA-256 and writes only hashes into the ACL policy. It prints paths, not secrets.

If any target exists, it aborts before reading/writing anything. In that case,
YOU must inspect your existing configuration and merge the exact policy below.
Do not paste secrets into chat. All newly generated runtime files are ignored
by Git and Docker build contexts. `.env` and existing JWT keys remain untouched.

The generated `.runtime/{api,scheduler,fetcher,processor}.env` files provide each
service's named Redis URL; fetcher/processor also get their own S3 keys.
`.runtime/bootstrap.env` holds a separate S3 bootstrap admin, never given to
workers. `.runtime/redis-health.env` supplies REDISCLI_AUTH for the PING-only user.
`.runtime/proof.env` supplies a host-side scheduler URL and a proof account password.
The script is HUMAN-RUN ONLY, and no agent has invoked it.

## Exact Redis policy template

Replace each angle-bracketed placeholder with the SHA-256 digest of that role's
independently generated password (the script performs this substitution).
Redis 7 selectors deliberately bind commands to the corresponding namespaces:
API's SET permission on rate buckets must not allow SET on job streams.

```text
user default off
user api reset on #<API_PASSWORD_SHA256> -@all +ping +hello +client|setname (+get +set +exists ~denylist:*) (+evalsha +eval +script|load +get +set +time ~warden:rate:*) (+xadd +xgroup|create ~warden:jobs:ingress) (+xrange +xinfo|stream ~warden:events) (+subscribe +unsubscribe +ping &warden:events:live)
user scheduler reset on #<SCHEDULER_PASSWORD_SHA256> -@all +ping +hello +client|setname (+get ~warden:metrics:*) (+xinfo|groups ~warden:jobs:*) (+evalsha +eval +script|load +exists +get +set +incr +pexpire +del ~warden:coord:lease:scheduler ~warden:coord:fence:scheduler) (+scan +exists ~warden:coord:members:fetchers:*) (+xadd +xgroup|create ~warden:jobs:*)
user fetcher reset on #<FETCHER_PASSWORD_SHA256> -@all +ping +hello +client|setname (+incrby ~warden:metrics:reclaimed) (+set +exists +scan ~warden:coord:members:fetchers:*) (+xadd +xgroup|create +xreadgroup +xack +xautoclaim +xpending +xclaim +evalsha +eval +script|load ~warden:jobs:*) (+xadd +xgroup|create ~warden:results) (+evalsha +eval +script|load +time +zadd +zrangebyscore +zrem +xadd +xgroup|create +incrby ~warden:retry:fetch:* ~warden:jobs:* ~warden:metrics:retries) (+xadd ~warden:dead:fetch) (+evalsha +eval +script|load +get +set +exists +del +incr +zrange +zrem +zadd +zcard +zpopmin +expire +ttl +pttl +pexpire ~warden:cache:robots:*)
user processor reset on #<PROCESSOR_PASSWORD_SHA256> -@all +ping +hello +client|setname (+incrby ~warden:metrics:reclaimed) (+xgroup|create +xreadgroup +xack +xautoclaim +xpending +xclaim +evalsha +eval +script|load ~warden:results) (+xadd ~warden:dead:processor) (+evalsha +eval +script|load +get +set +xadd ~warden:events ~warden:eventids:*) (+publish &warden:events:live)
user health reset on #<HEALTH_PASSWORD_SHA256> -@all +ping +hello +client|setname
```

`SCAN` is advisory and does not provide key-name privacy. Fetchers can discover
only protocol-prefixed queues in their application code but Redis SCAN itself
can reveal other key names. No service gets KEYS, CONFIG, FLUSHALL, ACL, or blanket
+@all. These commands are used only by the isolated private test fixture's admin.

## Exact SeaweedFS JSON template

```json
{
  "identities": [
    {"name": "fetcher", "credentials": [{"accessKey": "<FETCHER_ACCESS>", "secretKey": "<FETCHER_SECRET>"}], "actions": ["Read:warden", "Write:warden"]},
    {"name": "processor", "credentials": [{"accessKey": "<PROCESSOR_ACCESS>", "secretKey": "<PROCESSOR_SECRET>"}], "actions": ["Read:warden"]},
    {"name": "bootstrap", "credentials": [{"accessKey": "<BOOTSTRAP_ACCESS>", "secretKey": "<BOOTSTRAP_SECRET>"}], "actions": ["Admin", "Read", "Write", "List"]}
  ]
}
```

The processor cannot upload/delete objects. The bootstrap service creates the
bucket, then exits; it alone receives the admin identity. The API receives no
S3 identity. The Redis ACL mount contains hashes and is readable by the Redis
image's unprivileged reader; S3 configuration/runtime env files are mode 0600.
If the current SeaweedFS image runs without permission to read its bind-mounted
file, the HUMAN must grant that container UID read access without broadening the
worker identities. Never solve this with privileged/cap_add/daemon changes.

## Bring up and verify after provisioning

```bash
docker compose up --build -d
make check
uv run pytest libs/warden_redis/tests -m integration -q
```

Never paste `docker compose config`, container environments, or credential-bearing
logs into chat. `docker compose ps --services --status running` is safe status
output. Image isolation and S3 denial checks are part of the Gate 2 script.
The agent should resume live checks only after you confirm provisioning is done.

For the host-side proof, set WARDEN_DATABASE_URL in your own shell to the existing
PostgreSQL async URL using 127.0.0.1:5433 (supply your own existing credentials,
percent-encoded; do not share them). Then run:

```bash
uv run --env-file .runtime/proof.env python scripts/chaos_queue_proof.py --jobs 500 --kill-workers
```

The proof creates its own monitor/account and audit/job data, never deletes
existing rows or volumes, and restarts the workers it kills in a finally block.
Randomized killing applies only to `fetcher` and `processor`, never PostgreSQL,
Redis, object storage, or unrelated containers. Read the proof's assumptions in
the report: this is a worker-crash proof, not protection against destroyed Redis
storage or an indefinitely unavailable dependency.
